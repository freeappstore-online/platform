# Native store data reconciliation

Checked 2026-11-28 against platform source `23bdda1f` and Run source `47af5198` (clean local checkout). This narrows the questions in the [Apple](../ios/store-submission-readiness.md) and [Google](../android/store-submission-readiness.md) readiness sheets. It records implementation and configuration evidence, not submitted store declarations or unknown operator practices. Follow-up: [#867](https://github.com/freeappstore-online/platform/issues/867).

## IP processing and actual retention

| Flow | Fields and recipient | Retention supported by source |
| --- | --- | --- |
| Native pairing start and QR redemption | Backend reads `cf-connecting-ip` (fallback `unknown`); stores `nativepair:<SHA256(IP)>` or `nativecode:<SHA256(IP)>` in D1 `app_proxy_usage.app_id`, with UTC `day` and integer `count`. No raw IP column, account ID or device ID in these rows. | `pruneUsage` deletes days older than yesterday at daily 03:00 UTC. Under a successful schedule, a day's rows last approximately 27–51 hours from creation; failures can extend this. |
| Email magic-link authentication, if used | Same counter table stores `magic:<SHA256(email)>:<SHA256(IP)>`, `magic:<SHA256(email)>`, and `magicip:<SHA256(IP)>`; these associate pseudonymous email and network identifiers. | Same prune and backup behavior as pairing counters. |
| Counter and SDK-log backups | Custom daily 04:00 UTC JSON export explicitly includes `app_proxy_usage`, `app_logs` and `users`, among other tables. Destination: `fas-backups/db-backups/YYYY-MM-DD/fas.json`. | No expiry or deletion is implemented by `backup.ts`; no lifecycle for `fas-backups` is declared in repo. Live expiry could not be read (403), so it is **unknown**, not proven absent. Active-table pruning does not remove archived copies. |
| Location and generation records | Native location rows: grant/point IDs, recorded time, latitude, longitude, accuracy. Generation events: account/app/job IDs, runner, outcome, event time and allowlisted diagnostic record. | Active location rows expire at seven days, generation events at fourteen days, both via 15-minute cleanup. Neither table family is in the custom JSON export. Automatic D1 recovery history is separate. |

Evidence: [native-auth.ts](../packages/backend/src/routes/native-auth.ts), [nativeHash and pruneNativeData](../packages/backend/src/lib/native-companion.ts), [proxy-rate-limit.ts](../packages/backend/src/lib/proxy-rate-limit.ts), [auth.ts](../packages/backend/src/routes/auth.ts), [counter schema](../packages/backend/migrations/0006_app_secrets.sql), [scheduler](../packages/backend/src/index.ts), [backup.ts](../packages/backend/src/lib/backup.ts), [generation.ts](../packages/backend/src/routes/generation.ts).

**The IP hash does not rotate daily.** It is unsalted SHA-256 of the IP alone; the UTC day is a separate database key. Treat it as a stable pseudonymous network identifier, not anonymized data. Its absence from a direct account column does not establish unlinkability, especially for email-pair counters or infrastructure metadata. No IP geolocation is implemented in the native routes. Apple's [IP guidance](https://developer.apple.com/app-store/app-privacy-details/) maps IP according to its use; security identifiers are supported here, but a speculative Coarse Location declaration is not supported by these routes alone.

Cloudflare's [D1 recovery documentation](https://developers.cloudflare.com/d1/reference/time-travel/) says Time Travel is always on, retaining history for seven days on Free or thirty on Paid. The actual account plan was not verified. A location row can therefore remain in recovery history after its active-table deletion; “seven days” is not a verified upper bound for every copy. The public [privacy source](../sites/storefront/privacy.html) now narrows the location backup exclusion to daily database exports and explicitly acknowledges managed recovery history of up to thirty days, depending on plan. It does not claim IP hashes are anonymous. Its general deletion paragraph already acknowledges operational backups.

## Logs and infrastructure: what is established

- Native Swift/Kotlin source has no calls to the platform `/analytics/event` or SDK `/apps/:id/logs` endpoints. Local OS run logs are not evidence of remote crash reporting. Contribute **does** explicitly upload diagnostics; no analytics SDK is needed for that collection.
- Generation records allow error text, app/OS/device versions, network, thermal/battery/charging state, foreground/background, stage/CPU durations, memory, audio size/duration and realtime factor. Account, app and job linkage is supplied by the backend. Strings are bounded but not automatically stripped of every possible personal detail. No IP, track, input text or audio field is accepted in the diagnostic record. Audio is a separate result upload.
- The API has no generic request-logging middleware in `index.ts`; it does emit unhandled exception objects to `console.error`. Generation verification emits submission ID and error; cron emits error/result summaries. This does **not** prove Cloudflare stores no request metadata. `freeappstore-host` forwards API requests by service binding; its source adds no general access log.
- The separate web SDK log endpoint stores app/user IDs, client and ingestion timestamps, level, category, message, JSON data and build metadata; owners can query their apps' rows. Active rows are pruned daily after seven days and included in custom backups. These are web-app logs, not an implemented native-client SDK-log upload.
- Web app analytics receives IP in memory for per-app/kind sampling and writes app ID, event kind, path, referrer hostname, country from Cloudflare, user-agent class, custom properties and event time to Analytics Engine. Neither IP nor account ID is written by that path. It is an external web-app flow, not proof the native Store search/favourites are uploaded. Any web flow launched by the companion must be assessed in its own scope.

Evidence: [API error handler](../packages/backend/src/index.ts), [host](../workers/host/src/index.ts), [SDK logs](../packages/backend/src/routes/logs.ts), [analytics ingestion](../packages/backend/src/routes/analytics.ts), [native generation](../ios/FreeAppStore/Generation.swift), [Android source](../android/app/src/main/java/online/freeappstore/companion), [deployment config](../packages/backend/wrangler.toml). Backend and host Wrangler files declare no observability/logpush configuration. Omission is not a live setting check.

A read-only metadata check with the existing scoped `fas/CF_API_TOKEN` returned **HTTP 403** for both Workers' settings, `fas-backups` lifecycle and account/zone Logpush jobs. No log contents, backup objects, user records, credentials or destination secrets were printed or read. Local sanitized evidence: `build/native-data-audit/cloudflare-settings.json`. This proves insufficient read access, not that logging is disabled. Still needed: enabled invocation/console logs, sampling, downstream destinations, backup lifecycle and applicable plan/recovery window. Provider defaults are not a substitute for those facts; [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) retention depends on plan and is changing after this check date.

## Run versus independent publishers

**Run is the only curated location recipient.** The registry attributes `run` to `creatorGithub: serge-ivo`, developer FreeAppStore, repository `freeappstore-online/run`. This supports the intended first-party route; a shared GitHub organization or generic developer label alone would not prove all catalogue publishers are first party. Legal controller identity still needs to match the Store seller/account holder.

Location consent is explicit, versioned to the disclosure and bound to the current app owner. Owner changes invalidate the grant. Reading requires a session whose audience is `run` and returns only the same user's points; the creator/console has no location-read route. Run's [native source](https://github.com/freeappstore-online/run/blob/47af51982b9bd075f9dedb21be2fc4f831b4eb02/web/src/native.ts) reads missing intervals for an active recording; its [storage](https://github.com/freeappstore-online/run/blob/47af51982b9bd075f9dedb21be2fc4f831b4eb02/web/src/storage.ts) keeps saved runs in browser IndexedDB and drafts/plans in localStorage. It does not upload completed workout summaries through these modules. The companion uploads full coordinates/time/accuracy for the exercise-recording purpose; it does not upload heart rate, steps or calculated workout totals.

**Fitness classification is a concrete interpretation question, not missing implementation evidence.** Apple and Google define Fitness broadly to include exercise/physical activity, without requiring HealthKit. The deliberate run/walk recording purpose supports preparing optional, account-linked Fitness / Fitness info for App Functionality alongside Precise Location. Do not claim an extra heart-rate/health database or upload of Run's local summaries. Final form mapping should record this reasoning rather than asking the owner to guess what the code sends. Sources: [Apple types](https://developer.apple.com/app-store/app-privacy-details/), [Google types](https://support.google.com/googleplay/android-developer/answer/10787469).

**Contribute recipients can be independent publishers.** `ownerJobs` in [generation.ts](../packages/backend/src/routes/generation.ts) exposes contributor user ID/login, submissions, reports/notes, outcomes and diagnostic attempts to the app's owner, including failed attempts. Public accepted audio has no contributor in its public manifest. This is not equivalent to Run's same-user-only location access. Native opt-in and a privacy-policy link alone do not establish Google's consent exception for every publisher-visible diagnostic field. Prepare sharing for the known publisher-visible types unless the specific disclosure/consent and recipient relationship support an exception. Cloudflare hosting is a service-provider relationship in the implementation; independent app creators must not automatically be treated as processors. [Google's definitions](https://support.google.com/googleplay/android-developer/answer/10787469) distinguish these cases.
